🔐 Fluxo de Autenticação - Better Auth

Sistema de autenticação completo do Houston IV

📋 Visão Geral

O Houston IV utiliza o Better Auth, uma biblioteca moderna de autenticação para aplicações fullstack. O sistema implementa autenticação com múltiplos métodos, gerenciamento de sessões via cookies, e controle de acesso baseado em roles (RBAC).

🔑 Métodos de Autenticação

  • Email + Senha
  • OAuth (Google/Microsoft)
  • Magic Link (Email)

🛡️ Segurança

  • Sessions via cookies HTTP-only
  • CSRF protection
  • Password hashing (bcrypt)

👥 Controle de Acesso

  • RBAC (Role-Based Access Control)
  • Permissions granulares
  • Guards customizados

⚙️ Infraestrutura

  • PostgreSQL + Prisma
  • Next.js Proxy para cookies
  • NestJS Backend API

⚙️ Configuração do Better Auth

🔧 Backend - auth.config.ts API

Configuração central do Better Auth no backend NestJS:

  • Base URL: http://localhost:3001
  • Base Path: /auth (rotas em /api/auth/*)
  • Adapter: Prisma (PostgreSQL)
  • Secret: BETTER_AUTH_SECRET (env var)
  • Session: 7 dias de validade
  • Cookie Cache: 5 minutos
export const auth = betterAuth({ secret: process.env.BETTER_AUTH_SECRET, baseURL: 'http://localhost:3001', basePath: '/auth', database: prismaAdapter(prisma, { provider: 'postgresql', }), emailAndPassword: { enabled: true, minPasswordLength: 8, }, socialProviders: { google: { ... }, microsoft: { ... }, }, session: { expiresIn: 60 * 60 * 24 * 7, // 7 days cookieCache: { enabled: true, maxAge: 60 * 5, // 5 minutes }, }, })

🔄 Fluxo Completo de Autenticação

1️⃣ Usuário acessa a tela de login

Frontend: /apps/web/src/app/(auth)/auth/login/page.tsx

Componente <LoginForm /> renderizado com opções de autenticação

2️⃣ Usuário escolhe método de autenticação

📧 Email + Senha
🔗 Google OAuth
🔗 Microsoft OAuth
✨ Magic Link

3️⃣ Cliente de autenticação processa requisição

Arquivo: /apps/web/src/lib/auth-client.ts

Hook useAuth() chama funções do authClient:

  • signIn.email({ email, password })
  • signIn.social({ provider: 'google' })
  • signIn.magicLink({ email })

4️⃣ Requisição enviada ao Proxy Next.js

Arquivo: /apps/web/src/app/api/auth/[...all]/route.ts

Por quê? Resolve problema de cookies cross-domain!

  • Frontend: http://localhost:3000
  • Backend: http://localhost:3001
  • Proxy garante que cookies sejam do mesmo domínio (localhost:3000)
// Proxy forwards to NestJS API const url = `${API_URL}/api/auth/${path.join('/')}` const response = await fetch(url, { method: request.method, headers: { 'Cookie': request.headers.get('Cookie'), ... }, credentials: 'include', })

5️⃣ Backend processa autenticação

Arquivo: /apps/api/src/auth/auth.controller.ts

Controller captura todas as rotas /api/auth/* e delega ao Better Auth:

@Controller('auth') export class AuthController { private handler = toNodeHandler(auth) @Public() @All('*path') async handleAuth(@Req() req, @Res() res) { return this.handler(req, res) } }

Better Auth valida credenciais, cria sessão e gera cookie HTTP-only

6️⃣ Sessão armazenada no banco de dados

Database: PostgreSQL via Prisma

Tabelas criadas pelo Better Auth:

  • user - Dados do usuário
  • session - Sessões ativas
  • account - Contas OAuth vinculadas
  • verification - Tokens de verificação

7️⃣ Cookie enviado ao cliente

Proxy Next.js repassa o cookie Set-Cookie para o navegador

  • Nome: better-auth.session_token
  • Flags: HttpOnly, Secure, SameSite=Lax
  • Validade: 7 dias

8️⃣ Cliente atualiza estado da sessão

Hook: useSession() do Better Auth React

Estado atualizado automaticamente:

const { data: session, isPending } = useSession() // session.user contém: { id: 'user-id', email: 'user@example.com', name: 'Nome do Usuário', role: 'escalista', grupoIds: [...] }

9️⃣ Redirecionamento para área autenticada

Hook useAuth() executa:

await refetch() // Atualiza sessão router.replace('/') // Redireciona para home

🛡️ Proteção de Rotas

Frontend - Protected Routes

🔒 ProtectedRoute Component

Arquivo: /apps/web/src/components/auth/protected-route.tsx

export function ProtectedRoute({ children }) { const { isAuthenticated, isLoading } = useAuth() if (!isLoading && !isAuthenticated) { router.push('/auth/login') } if (!isAuthenticated) return null return <>{children} }

Verifica isAuthenticated e redireciona se necessário

Backend - Auth Guards

🛡️ AuthGuard

Arquivo: /apps/api/src/auth/guards/auth.guard.ts

Processo:

  1. Verifica se rota é @Public()
  2. Lê sessão do Better Auth em request.session
  3. Busca roles e permissões do usuário
  4. Popula request.user com dados completos
  5. Permite ou nega acesso
const authenticatedUser = { id: sessionUser.id, email: sessionUser.email, roles: userPermissions.roles, permissions: userPermissions.permissions, grupoIds: [...], hospitalIds: [...], } request.user = authenticatedUser
➡️

👮 RolesGuard

Verifica se usuário possui roles necessárias

@Roles('admin', 'gestor') @Get('sensitive-data') getData() { // Apenas admin ou gestor }
➡️

🔑 PermissionsGuard

Verifica permissões granulares

@RequirePermissions('escalas:write') @Post('escalas') createEscala() { // Requer permissão específica }

🔐 Métodos de Autenticação

📧 Email + Senha

Fluxo:

  1. Usuário submete formulário com email e senha
  2. signIn.email({ email, password })
  3. Better Auth valida credenciais (bcrypt)
  4. Sessão criada e cookie enviado
  5. Redirecionamento para home

Config: Senha mínima de 8 caracteres

🔗 OAuth (Google/Microsoft)

Fluxo:

  1. Usuário clica no botão social
  2. signIn.social({ provider: 'google' })
  3. Redirecionado para OAuth provider
  4. Após autorização, retorna com code
  5. Better Auth troca code por tokens
  6. Busca dados do usuário
  7. Cria/atualiza usuário e sessão
  8. Cookie enviado e redirecionamento

Config:

  • Google: GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET
  • Microsoft: MICROSOFT_CLIENT_ID, MICROSOFT_CLIENT_SECRET

✨ Magic Link

Fluxo:

  1. Usuário insere email
  2. signIn.magicLink({ email })
  3. Better Auth gera token único
  4. Email enviado com link mágico
  5. Usuário clica no link
  6. Token validado e sessão criada
  7. Cookie enviado e redirecionamento

Vantagem: Login sem senha, mais seguro

⚡ Por que usar Proxy Next.js?

Sem o proxy, o frontend (localhost:3000) e backend (localhost:3001) seriam domínios diferentes, causando problemas com cookies devido à política Same-Origin. O proxy Next.js em /api/auth/* encaminha todas as requisições para o backend, mas mantém os cookies no domínio do frontend, garantindo que funcionem corretamente.
